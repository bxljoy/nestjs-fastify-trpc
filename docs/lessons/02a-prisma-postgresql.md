# Lesson 02A — Prisma and PostgreSQL persistence

## What exists now

A Nest-managed Prisma client can create and retrieve Campaign records from PostgreSQL. A SQL migration creates the table and a database CHECK constraint rejects negative budgets.

There is **no campaign HTTP endpoint yet**. The integration test is our first consumer. Your Health and Hello endpoints are unchanged and still work without PostgreSQL.

This lesson intentionally separates learning persistence from learning tRPC.

## 1. Three different things

| Component | What it does | Rough Spring/JPA comparison |
|---|---|---|
| PostgreSQL | Stores data and enforces relational constraints | The database, unchanged in principle |
| Prisma schema / CLI | Describes models, generates client code, and manages migration files | Parts of entity mapping plus migration tooling, but not a direct JPA equivalent |
| Prisma Client | Executes explicit, typed database operations | A typed query API rather than an EntityManager/unit-of-work |

Nest organizes and injects the client; Prisma does not replace Nest, and neither replaces PostgreSQL.

The flow for this lesson is:

```text
Jest integration test
  → Nest TestingModule imports PrismaModule
  → injected PrismaService
  → generated PrismaClient
  → PrismaPg adapter / pg connection pool
  → PostgreSQL
```

## 2. A schema is not a table

Read `apps/api/prisma/schema.prisma`:

```prisma
model Campaign {
  id               String   @id @default(uuid()) @db.Uuid
  name             String   @db.VarChar(200)
  dailyBudgetMinor Int
  currency         Currency @default(EUR)
  createdAt        DateTime @default(now()) @db.Timestamptz(3)
}
```

This is a declarative model used for client generation and migration planning. Editing this file alone does not change PostgreSQL.

There are two different outputs:

```text
schema.prisma
  ├── prisma generate → TypeScript client/types
  └── prisma migrate → SQL migration history → database schema
```

The initial integration test demonstrated this: the generated client existed and the database connection worked, but the query failed because `public.Campaign` did not exist. TypeScript knowing a model does not prove the database has its table.

## 3. Why a migration file?

The migration lives under:

```text
apps/api/prisma/migrations/20261001082131_init_campaign/migration.sql
```

It creates the EUR enum and Campaign table, then adds:

```sql
ALTER TABLE "Campaign"
ADD CONSTRAINT "Campaign_dailyBudgetMinor_nonnegative"
CHECK ("dailyBudgetMinor" >= 0);
```

A migration is a reviewable record of a schema change. It gives another checkout or database a repeatable route to the same structure. Prisma records applied migration history in `_prisma_migrations`.

We generated the initial SQL with `migrate dev --create-only`, reviewed it, added the CHECK, and only then applied it. **Do not modify a migration after it has been applied to shared databases**; add another migration instead.

The CHECK is explicitly maintained in SQL because not every PostgreSQL constraint has a matching Prisma schema declaration. Remember it when reviewing future migrations.

- `migrate dev`: development workflow for generating/applying changes, with a shadow database used for checks. It can request a reset when there is drift; do not accept automatically.
- `migrate deploy`: applies existing migration files. Our integration runner uses this; it does not invent a schema or reset tables.

Prisma's `@default(uuid())` is generated by the Prisma client, not a PostgreSQL UUID default in this SQL. Direct SQL inserts must provide the ID. By contrast, `createdAt` has a database `CURRENT_TIMESTAMP` default in the migration.

## 4. Money is an integer, with a database invariant

`dailyBudgetMinor: 10000` means EUR 100.00. We store cents, not a JavaScript decimal such as 100.10.

This avoids the usual binary floating-point representation problem for decimal currency. It does not make all future arithmetic automatically safe: percentage calculations still need an explicit integer/rounding policy.

The PostgreSQL INTEGER column accepts signed 32-bit values. Combined with the CHECK, this lesson's budget range is 0 through 2,147,483,647 cents. Future public input validation must respect that database bound, not merely JavaScript's much larger safe-integer bound.

The EUR enum limits currency to the single supported teaching currency. Multiple currencies are a future data-model decision, not a field where arbitrary strings are silently accepted.

Why enforce the budget rule in the database as well as future API validation? API validation cannot protect writes from another service, a migration, or a SQL console. The database is the shared final boundary. Later Zod validation will provide friendlier errors earlier.

## 5. Generate a client that fits this project

The generator is explicit:

```prisma
generator client {
  provider               = "prisma-client"
  output                 = "../src/generated/prisma"
  moduleFormat           = "cjs"
  generatedFileExtension = "ts"
  importFileExtension    = ""
}
```

Prisma 7's new generator writes plain TypeScript into the specified directory. We select CommonJS-compatible generation and extensionless relative imports to match our existing backend/test compilation.

Run `pnpm db:generate` after schema changes and on a fresh checkout before typechecking/building. The generated directory is ignored by Git: the versioned schema and pinned Prisma version are the source of truth. Never hand-edit generated code.

Our import is from that generated output:

```typescript
import { PrismaClient } from '../generated/prisma/client';
```

We still install @prisma/client for its runtime support; using a generated output directory does not remove that dependency.

## 6. PrismaModule and dependency visibility

Read `apps/api/src/prisma/prisma.module.ts`:

```typescript
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
```

This should now look familiar:

- Register PrismaService as a managed dependency.
- Export it so an importing feature module can inject it.
- No controller is needed because this module owns infrastructure, not an HTTP endpoint.
- No `@Global()` is used; consumers must explicitly declare the dependency.

The test imports PrismaModule. **AppModule does not yet import it**, because no current HTTP feature uses a database. Creating a file does not activate its Nest module; the application graph controls that.

When a later CampaignsModule needs persistence, it will import PrismaModule and inject PrismaService. We will not repeat the provider registration in each consumer module.

## 7. Own the client's lifecycle

Read `apps/api/src/prisma/prisma.service.ts`.

The constructor validates that DATABASE_URL is present and supplies a PostgreSQL adapter:

```typescript
super({
  adapter: new PrismaPg({
    connectionString,
    connectionTimeoutMillis: 5000,
    max: 5,
  }),
});
```

The adapter manages a pg pool with at most five connections here. The connection timeout avoids an indefinite wait for a connection. These are local teaching defaults, not production capacity planning.

`PrismaService extends PrismaClient` makes the generated query API available directly on the injectable service. It avoids a generic repository wrapper that adds no value to this small example.

```typescript
async onModuleInit(): Promise<void> {
  await this.$connect();
}

async onModuleDestroy(): Promise<void> {
  await this.$disconnect();
}
```

Nest calls these lifecycle hooks when its module/application is initialized and closed. The corresponding TypeScript interfaces document/typecheck the method contracts; Nest invokes the named methods at runtime.

The testing container's `.compile()` constructs and resolves dependencies; `await moduleRef.init()` invokes initialization hooks. `await moduleRef.close()` invokes teardown and releases the client/pool. No Fastify app is necessary for a persistence-only test.

Create one managed client per intended container registration, not one per query or request. Pool ownership matters even when the current table is tiny.

## 8. Prisma is not JPA dirty checking

The integration test executes explicit operations:

```typescript
await prisma.campaign.create({
  data: { id, name: 'Campaign A', dailyBudgetMinor: 10000 },
});

const campaign = await prisma.campaign.findUniqueOrThrow({
  where: { id },
});
```

The generated types check model fields and query arguments. The returned record is plain data (with hydrated JavaScript values such as Date), not a managed entity attached to a Hibernate persistence context.

Mutating it does not send SQL:

```typescript
campaign.name = 'Only changed in memory';
```

Persistence requires an explicit update query. There is no automatic flush/dirty checking or transparent lazy-loading of associations. We are not adding a budget-update feature in this lesson; this comparison explains the model, not new functionality.

## 9. Separate development and test databases

`compose.yaml` defines two services bound only to loopback:

| Service | Host port | Database | Storage |
|---|---|---|---|
| postgres | 55432 | budget_review_dev | Named persistent volume |
| postgres-test | 55433 | budget_review_test | Disposable tmpfs |

The public credentials are local examples only. The development `.env` is ignored by Git, while `.env.example` is committed.

Prisma 7 CLI reads the connection from `prisma.config.ts`. Our development commands explicitly load `.env` using Node's `--env-file` option. An already exported environment value wins over the file, so inspect the displayed datasource before a migration.

The runtime PrismaService reads process.env; it does not implicitly load the CLI configuration. The integration runner supplies its own fixed test URL and ignores an inherited DATABASE_URL for this purpose. It never loads the development env file.

The Compose image used in verification was PostgreSQL 17.11, digest `postgres@sha256:639ab7ceb90e13123085b741fb31ef493fba25463002f6da665352e7b534b652`. The `17-bookworm` tag can receive updates; inspect and reverify when it changes.

## 10. What the integration tests prove

Read `apps/api/test/campaign.persistence.integration-spec.ts`.

1. The Nest testing module imports PrismaModule.
2. Initialization connects the client.
3. One test inserts a campaign and reads its fields/defaults back from PostgreSQL.
4. Another attempts a negative budget and verifies PostgreSQL SQLSTATE `23514` (CHECK violation) and the named budget constraint, then checks no record was persisted.
5. Teardown deletes only the UUIDs allocated by this test and closes the module, even if row cleanup fails.

The error assertion is more specific than “any exception happened”: a connection error is not evidence that PostgreSQL enforces the budget rule. The exact error-wrapper shape is tied to the pinned adapter version and must be reviewed on upgrades.

We also verified regression sensitivity in the disposable database: temporarily removing the CHECK allowed the negative write and made the test fail. Restoring the same constraint returned it to green. Do not repeat this against development/shared data.

`pnpm test` still runs the six HTTP/DI tests, without PostgreSQL. `pnpm test:db` opts into the two database tests and applies reviewed migrations first. The integration filename/config prevents accidental selection by normal Jest patterns. Both configurations still typecheck through our main TypeScript check.

These are real PostgreSQL integration tests. SQLite or a mocked Prisma client would not prove this migration, enum, CHECK constraint, or driver's error behavior.

## Commands and stopping point

From a fresh checkout, after selecting a supported Node 24 version:

```bash
pnpm install --frozen-lockfile
cp -n apps/api/.env.example apps/api/.env
pnpm db:generate
pnpm db:up
pnpm db:migrate
pnpm db:test:up
pnpm test:db
pnpm test
pnpm typecheck
pnpm build
```

When finished:

```bash
pnpm db:stop
pnpm db:test:stop
```

Stopping test PostgreSQL loses its tmpfs data by design; starting it again and running test:db recreates the schema from migrations. Development data persists. Do not delete the named volume as routine cleanup.

No CampaignsService, seed performance, campaign endpoint, frontend, or execution processor has been added. A transaction is not needed just to make one insert atomic—PostgreSQL already provides that. We will revisit explicit multi-operation transactions when approval and execution intent must succeed together.

The new Prisma dependency graph has known advisories; read [the dependency audit and bounded exposure assessment](../dependency-audit.md). Passing functional tests does not remove those findings.
